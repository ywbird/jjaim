# glyph-inspect: 선언형 글리프 검증 CLI 명세

## 목적과 작업 위치

이 디렉터리(`tools/inspector/`)에서 구현할 독립 CLI다. 프로젝트 루트의 [`SPEC.md`](../../SPEC.md) v0.3을 선언의 의미에 관한 정본으로 사용하고, [`hangul.json`](../../examples/hangul.json)을 대규모 입력 사례로 사용한다. **한글 전용 로직을 작성하지 않는다.** 다른 그룹·유니코드 범위도 같은 코드로 처리한다.

이 프로그램은 선언에서 유니코드 대응을 풀고, 글리프의 출처를 조사하고, 실제 텍스처를 조합해 PNG로 검증한다. **TTF 파일 생성 또는 TTF를 열어 재렌더링하는 프로그램은 아니다.** 여기서 '생성된 글리프'란 선언의 조합 결과를 실제 텍스처 화소로 렌더링한 글리프다.

`examples/hangul.json`이 참조하는 `examples/hangul.png`는 프로젝트 루트에서 `python3 tools/font_bin_to_png.py examples/hangul.bin`으로 생성한다. **`list`·`groups`는 PNG 없이도 성공해야 하고**, `sheet`·`text`는 참조한 PNG가 없으면 경로를 알리는 오류를 내야 한다. 목록의 리소스 독립성 테스트에는 선언 JSON만 임시 디렉터리에 복사하고, 이미지 동작 테스트에는 작은 임시 PNG를 생성한다. 없는 텍스처를 빈 글리프로 대체해서는 안 된다.

## CLI 계약

uv 프로젝트로 구성하고 `uv run glyph-inspect` 명령을 제공한다. 아래 옵션·서브커맨드는 실제로 실행 가능해야 한다. `<decl.json>`은 모든 서브커맨드의 필수 위치 인수다. `--help`에는 사용법과 각 옵션이 나온다.

```text
uv run glyph-inspect list   <decl.json> [--format text|json] [--output PATH]
uv run glyph-inspect groups <decl.json> [--format text|json] [--parts] [--output PATH]
uv run glyph-inspect sheet  <decl.json> --output PATH [--columns N] [--scale N]
                               [--border] [--box-kind cell|ink]
                               [--background white|transparent] [--per-page N]
uv run glyph-inspect text   <decl.json> (--text STRING | --text-file PATH)
                               --output PATH.png [--scale N]
                               [--background white|transparent]
```

- `list`와 `groups`의 기본 `--format`은 `text`, 기본 출력은 UTF-8 표준 출력이다. `--output`을 주면 해당 파일에 기록한다. 진단 메시지는 표준 오류에만 쓴다. 이미지 명령은 파일 경로를 필수로 받으며 표준 출력에 이미지 바이트를 내보내지 않는다.
- `--scale`은 양의 정수, 기본 2다. 글리프를 논리 픽셀 해상도로 먼저 조합하고 **최근접 이웃**으로 정수 배 확대한다. `--columns`는 양의 정수, 기본 64다.
- `--text-file -`은 표준 입력의 UTF-8 바이트를 읽는다. 셸 인수에는 NUL을 넣을 수 없으므로 U+0000을 포함한 입력 시험에는 파일/표준 입력을 쓴다. 디코딩 실패는 오류다.
- 선언 파일을 찾을 수 없거나 읽을 수 없으면 설명 가능한 오류로 종료한다. `--output`의 부모 디렉터리는 존재해야 한다(페이지 모드의 출력 디렉터리 자체는 생성 가능). 같은 출력에 재실행하면 결정적으로 덮어쓴다.

### `list`: 생성되는 유니코드 목록

모든 그룹의 `unicode` 매핑을 합쳐 **숫자 코드 포인트 오름차순**으로 한 번씩 출력한다. 실제 그림이 비어 있어도 매핑되어 있으면 포함한다. PNG는 읽지 않는다.

- 텍스트: 한 줄에 `U+AC00\t가` 형식. 제어 문자·탭·줄바꿈 등 표시할 수 없는 문자는 실제 문자를 출력하지 않고 `\u0000` 같은 이스케이프 표기로 적는다(원시 NUL/개행이 출력 행을 깨뜨리지 않아야 함).
- JSON: 코드 포인트 순서의 배열. 예: `[{"codepoint":"U+AC00","character":"가"}]`. JSON 규격에 맞게 제어 문자를 이스케이프한다. 코드 포인트 표기는 최소 네 자리 이상의 대문자 16진수 `U+XXXX`다.

### `groups`: 코드 포인트마다 참여하는 그룹

`list`와 같은 코드 포인트들을 출력하되, 해당 결과 글리프에 **구조적으로 참여하는 그룹 이름**을 포함한다. 출력 그룹 자신을 첫 번째로 넣고, 임포트 순서에 따른 깊이 우선 순회에서 처음 만난 그룹을 뒤에 더한다. 같은 그룹을 여러 번 임포트했다면 `groups` 배열에는 첫 등장만 남긴다. 글리프가 투명하거나 부모에서 전부 잘려도 선언상 참조했다면 포함한다. PNG는 읽지 않는다.

- 텍스트: `U+AC00\t가\thangul_syllables,initial_0,medial_0` 형식.
- JSON: `[{"codepoint":"U+AC00","character":"가","groups":["hangul_syllables","initial_0","medial_0"]}]` 형식.
- 선택적인 `--parts`: JSON 결과의 각 항목에 `parts` 배열을 추가한다. 텍스처를 가진 원본 글리프의 **배치 발생 건별** `group`, `index`, `offset`(출력 글리프 원점 기준 누적 `[x,y]`)을 실제 레이어 순서대로 기록한다. 같은 그룹이 두 번 들어오면 두 건을 유지한다. 텍스처 없는 중간 그룹은 `groups`에는 들어가지만 `parts`에는 들어가지 않는다. PNG의 화소 존재 여부는 확인하지 않으므로 클리핑으로 보이지 않는 배치도 나열한다. `--parts`를 텍스트 형식과 함께 사용하면 인수 오류를 낸다.

### `sheet`: 생성 글리프 전체 목록 이미지

모든 **매핑된 코드 포인트**의 글리프를 순서대로 렌더링해 PNG 한 장에 격자로 배치한다. 각 슬롯에는 실제 조합 글리프와 `U+XXXX` 라벨을 함께 넣는다. 유니코드 별칭이 같은 글리프를 가리켜도 코드 포인트별 슬롯을 하나씩 만든다. 매핑이 하나도 없으면 오류다. 페이지 크기·라벨은 서로 다른 그룹 크기에서도 잘리지 않게 전체 결과 그룹의 최대 가로·세로 크기를 기준으로 산정한다. 각 글리프는 슬롯의 왼쪽 위에 놓는다.

- 기본은 **모든 글리프를 한 이미지에 담는다**. 이때 `--output`은 PNG 파일 경로다. 이미지 크기가 1억 화소를 넘거나 한 변이 32768픽셀을 넘으면 일부만 저장하지 말고, 페이지 분할을 요청하라는 오류를 낸다. 페이지 분할을 지정했어도 개별 페이지가 이 한도를 넘으면 오류를 낸다.
- `--per-page N`을 지정하면 `--output`은 디렉터리 경로다. 코드 포인트 순서대로 N개씩 `page-0001.png`, `page-0002.png` …에 저장하고, 같은 폴더에 `manifest.json`을 쓴다. 매니페스트에는 총 개수, 각 페이지 파일명·개수·첫/마지막 코드 포인트를 기록한다. 어떤 경우에도 글리프가 누락되거나 잘려서는 안 된다.
- `--border`는 **글리프 이미지의 경계**에만 1픽셀 윤곽선을 그린다(라벨과 슬롯 전체에는 그리지 않음). 기본 `--box-kind cell`은 출력 그룹의 실제 `size` 직사각형, `ink`는 렌더한 글리프의 알파가 0보다 큰 화소를 감싸는 최소 직사각형이다. 빈 글리프에는 `ink` 테두리를 그리지 않는다. 테두리는 글리프 화소를 덮지 않게 바깥쪽에 그리며, 슬롯에는 테두리가 잘리지 않을 여백을 둔다. `--border`가 없으면 테두리는 없다.
- 기본 배경은 흰색이고 `--background transparent`는 투명이다. 라벨과 테두리는 배경에 관계없이 읽을 수 있는 대비색을 쓴다. 글리프 모양 자체는 배경과 합성하기 **전**의 투명 RGBA 결과를 사용한다.

### `text`: 예시 텍스트 이미지

문자열의 각 유니코드 스칼라 값을 `unicode` 대응으로 조회하고 같은 조합 렌더러로 PNG에 그린다. `--text`와 `--text-file`은 정확히 하나 필요하다. **정규화, 자모 조합, 폰트 폴백, 글자 모양 치환, 커닝은 하지 않는다.** U+000A는 줄바꿈이며 CRLF와 단독 CR도 줄바꿈으로 정규화한다. 그 외 문자는 U+0000과 탭을 포함해 각 코드 포인트 하나로 취급한다.

- 매핑된 문자는 해당 결과 그룹의 `size` 가로폭만큼 전진한다. 줄 높이는 이 선언에서 매핑된 결과 그룹들의 최대 세로 크기다. 각 글리프는 줄의 위쪽에 정렬한다. 논리 픽셀 배치 후 최종 결과를 `--scale`배 한다.
- 없는 코드 포인트는 **U+0000이 매핑되어 있으면 그 글리프**를 대신 사용한다. 그 글리프가 비어 있어도 빈 박스를 그리지 않는다. 전진폭도 U+0000의 결과 그룹 폭을 사용한다.
- U+0000도 없다면 비어 있는 **윤곽선 박스**를 그린다. 박스의 논리 크기는 매핑된 결과 그룹의 최대 `(가로, 세로)`이며 검정 1픽셀 테두리와 투명 안쪽을 갖는다. 그 가로폭만큼 전진한다.
- 텍스트가 빈 문자열이거나 선언에 유니코드 매핑이 전혀 없으면 오류다. 빈 줄은 한 줄 높이만큼 차지한다. 마지막 줄바꿈도 마지막 빈 줄을 만든다. 실제 글리프·대체 글리프가 결과 캔버스 밖으로 잘리면 안 된다.

## 선언 해석과 렌더링 정책

파서와 검증기는 [`../../SPEC.md`](../../SPEC.md)의 그룹·임포트·유니코드 정의를 그대로 따른다. 특히 아래 항목은 빼먹지 않는다.

1. 최상위의 선택적 `metadata` 매핑과 그룹의 선택적 문자열 `description`을 읽고 자료형을 검증하지만 글리프 조합에는 사용하지 않는다. 최상위 `texture_sets`는 셋 이름 -> 소스 이름 -> 이미지 경로 문자열의 매핑만 담는다. 크기·절단 좌표 등 추출 정보는 셋에 두지 않는다. 그룹 `size`, `count`, 선택적 텍스처 참조 및 추출 정보(`set`, `source`, `start`, `direction`), 순서 있는 `imports`, 선택적 `unicode`를 읽는다. 없는 셋·소스와 잘못된 자료형은 PNG를 열지 않고 선언 오류로 거부한다. 텍스처 없는 조합 전용 그룹에는 `texture_sets`가 없어도 된다. `direction`의 `right|left|down|up`은 이 CLI에서 지원한다. 모든 인덱스는 0부터 시작한다.
2. `from: [a,b]`는 끝을 제외한다. `repeat`는 **배열**이며 각 축의 `count`, `from_stride`(기본 0), `to_stride`(기본 `b-a`)를 적용한다. 축을 생략하면 한 번 배치한다. 여러 축은 앞에서부터 바깥 반복이다. 해당 그룹의 모든 임포트 배치를 지정된 순서로 적용한다. 같은 원본을 여러 번 임포트해도 합치거나 덮어쓰지 않는다.
3. 원본 그룹의 최종 글리프를 자신의 `size`로 클리핑한 다음, 임포트의 단일 `offset`을 적용하고 부모의 `size`로 다시 클리핑한다. 텍스처를 가진 부모는 자기 텍스처 글리프가 첫 레이어다. 중첩 임포트도 지원하고 순환은 거부한다.
4. `unicode` 범위는 `from`의 연속 인덱스를 `to`부터 연속 코드 포인트에 매핑한다. 임포트는 자식의 유니코드 대응을 상속하지 않는다. 유효한 스칼라 값만 허용하며 **U+0000은 유효**하다. 같은 코드 포인트가 다른 `(그룹, 인덱스)`에 매핑되면 오류다. 같은 매핑의 중복은 한 항목으로 정규화한다. 다른 코드 포인트가 같은 결과 글리프를 가리키는 별칭은 허용한다.
5. 선언 파일은 UTF-8 JSON이며 `texture_sets`에 등록한 상대 이미지 경로는 **선언 파일이 있는 디렉터리**를 기준으로 해석한다. JSON 중복 키·잘못된 자료형·빈/역방향 범위·참조 오류·반복을 편 뒤 범위를 벗어나는 인덱스·순환 참조·유니코드 충돌은 명시적으로 거부한다. 이미지 명령에만 참조한 텍스처 파일이 필요하다(등록했지만 사용하지 않은 파일은 열지 않는다). 그때 참조한 글리프 절단 영역이 이미지 바깥이면 오류다. 이 CLI의 그룹 추출 방식은 연속된 같은 크기의 사각형에 한정되며, 불규칙한 박스 패킹 좌표를 별도로 지원하지 않는다.
6. 이미지 명령은 PNG를 RGBA로 디코딩한다. 부모의 텍스처 → 선언 순서의 임포트 레이어를 **source-over 알파 합성**한다. 임포트한 자식 글리프는 자식 크기의 투명 캔버스에 먼저 렌더링·클리핑한 뒤 부모에 합성한다. 흰색/투명 배경은 모든 글리프 조합을 완료한 **뒤** 미리보기 이미지에 적용한다. 이는 CLI가 명시적으로 선택한 렌더링 정책이지 선언 형식의 보편적인 합성 규칙이 아니다. 다른 렌더러는 마스크 합집합 등을 선택할 수 있다.
7. 결과는 순수한 픽셀 미리보기다. 별도의 기준선·advance·폰트 단위나 TTF 엔진의 글자 배치 결과와 동일하다고 주장하지 않는다. 백색 불투명 텍스처는 투명 영역으로 자동 간주하지 않는다. 알파가 없는 PNG는 불투명하게 처리한다.

## 검증 및 인수 기준

명령행 인수 오류는 종료 코드 2, 선언의 구문·의미 오류는 3, 필요한 텍스처/출력 경로 오류는 4, 성공은 0을 사용한다. 예상 가능한 오류는 간결한 이유와 그룹/인덱스/경로를 표준 오류에 적고 트레이스백을 보이지 않는다. 실패했을 때 잘못된 완성 이미지나 불완전한 페이지 묶음을 성공 결과처럼 남기지 않는다.

자동 테스트를 포함하여 최소한 아래를 확인한다.

- `examples/hangul.json`의 **JSON만 임시 디렉터리에 복사해 텍스처가 없는 상태에서도** `list`와 `groups`가 한글 `U+AC00`부터 `U+D7A3`까지 11,172개와 ASCII `U+0020`부터 `U+007E`까지 95개, 모두 11,267개를 출력한다. `가`(U+AC00)는 `hangul_syllables,initial_0,medial_0`, `각`(U+AC01)은 여기에 `final_0`가 붙는다. `나`(U+B098)는 ㄱ·ㅋ용 중성벌이 아닌 `medial_1`을 사용한다. 테스트는 나머지 한글 조합도 독립적인 8×4×4 벌 분류표에 따라 전수 비교한다.
- `examples/ascii.json`은 `U+0020`부터 `U+007E`까지 95자를 매핑하고, 같은 ASCII 그룹이 `examples/hangul.json`에도 들어 있다. 두 선언 모두 텍스처 없이 `list`·`groups`가 성공해야 한다.
- 각 `at`의 반복을 펼쳤을 때 실제 원본/대상 인덱스가 유효하고, 같은 결과에 여러 임포트가 들어오면 레이어와 `--parts`의 발생 건을 모두 보존한다. 8×4×4 입력에서 글리프마다 초성·중성 하나씩, 받침이 있을 때만 종성 하나가 나타난다.
- 테스트용 **임시 텍스처**로 글리프 크롭 위치, 오른쪽/왼쪽/위/아래 방향, 반복 축, 임포트 오프셋(음수 포함), 자식·부모 클리핑, 중첩 임포트, 반투명 RGBA 레이어 순서, 결과 픽셀을 확인한다. 여러 색/위치의 표식을 사용해 선택한 글리프가 진짜로 그려졌는지 검사한다.
- `sheet`의 슬롯 수·정렬·라벨·`--border`의 cell/ink 구분·페이지 매니페스트·누락 없는 페이지 분할을 검증한다. 실제 이미지 화소를 읽어 조합 결과가 예상과 같은지 검사한다.
- `text`의 매핑된 문자, 미매핑 문자(빈 박스), U+0000 매핑이 있을 때의 대체, 멀티라인·빈 줄, 텍스트 파일의 실제 NUL을 확인한다. U+0000이 매핑되어 있지만 그림이 빈 경우에도 빈 박스를 그리지 않아야 한다.
- 잘못된 JSON/중복 키, 잘못된 `texture_sets` 형식과 없는 셋/소스 참조, 범위 이탈, 자기/간접 순환, 유니코드 충돌, 없는 PNG를 거부한다. 없는 PNG여도 참조 이름이 유효하면 `list`·`groups`는 계속 성공한다. 한 셋의 복수 소스 및 서로 다른 셋에서의 같은 소스 이름도 확인한다. 알 수 없는 필드·지원하지 않는 이미지 형식도 조용히 무시하지 않고 보고한다.

`docs/`의 참고 문서는 수정하지 않고, 구현 코드·테스트·의존성 파일은 이 `tools/inspector/` 안에 둔다. `examples/`의 선언은 입력 사례이므로 예제 추가·보완은 허용하되, 기존 선언의 의미를 구현 편의를 위해 바꾸지 않는다. 새 기능을 위해 프로젝트 루트 `SPEC.md`의 의미를 임의로 바꾸지 않는다. 명세에서 해결되지 않은 선택이 있으면 구현 문서에 결정과 근거를 기록한다.
