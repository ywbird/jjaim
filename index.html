JJaim은 텍스처와 재사용 가능한 그룹으로 글리프를 구성하는 명세입니다. 한글은 그 활용 예 중 하나입니다. 함께 제공하는 예제는 344개 부품으로 한글 11,172자를 구성합니다.

이 페이지는 SPEC.md의 한국어 해설입니다. 의미의 기준은 원문이며, 현재 도구는 JSON을 읽지만 명세의 최종 저장 형식은 아직 정해지지 않았습니다. 원문 7절의 YAML도 설명용 표기입니다.

01

선언의 구조

원문 §1–2 ↗

이미지의 이름을 등록하고, 그룹에서 글리프를 정의합니다. 그룹을 가져올 때는 복사본이 아니라 이름을 참조합니다.

glyph definition
  • metadata선언 전체의 설명
  • texture_sets셋 이름 → 소스 이름 → 이미지 경로
  • groups
    • description
    • size / count
    • texture
    • imports → at → repeat
    • unicode
metadata
선택 사항입니다. name, version, author는 문자열이고, 추가 설명 필드도 둘 수 있습니다. 여기의 버전은 명세가 아닌 해당 선언의 버전입니다.
texture_sets
셋마다 소스 이름과 이미지 경로를 연결하는 레지스트리입니다. 소스 이름은 셋 안에서 구분합니다. 셀 크기·추출 위치·패킹·합성 방식은 여기에 넣지 않습니다.
groups
이름을 가진 글리프 묶음입니다. 각 그룹이 크기, 개수, 추출 설정, 가져오기, 문자 매핑을 소유합니다. description은 설명일 뿐 구성에는 영향을 주지 않습니다.

한 그룹을 여러 곳에서 참조할 수 있지만, 참조가 순환해서는 안 됩니다. 원문의 ADH 언급은 데이터 계층을 설명하기 위한 비유입니다. 항공 분야 스키마를 따르거나 설치할 필요는 없습니다.

02

텍스처와 좌표

원문 §2 ↗

그룹의 size는 글리프 한 개의 크기이고, count는 글리프의 개수입니다.

크기size: [8, 8]

너비·높이 모두 양의 정수

개수count: 6

유효 인덱스는 0부터 5까지

로컬 원점(0, 0)

왼쪽 위. x는 오른쪽, y는 아래쪽

모든 좌표·크기·오프셋은 같은 논리 픽셀 단위의 정수입니다. 로컬 경계는 [0, w) × [0, h)입니다. 텍스처가 없는 그룹은 빈 이미지에서 시작하며, 다른 그룹을 가져와 구성할 수 있습니다. 모든 그룹에 텍스처가 없다면 texture_sets도 생략할 수 있습니다.

그룹의 texture 필드
{
  "set": "main",
  "source": "sheet",
  "start": [0, 0],
  "direction": "right"
}

8 × 8 셀을 오른쪽으로 추출

0x = 018216324432540
시작점(i) = start + i × step

각 사각형의 왼쪽 위가 추출한 글리프의 로컬 원점이 됩니다. 이미지 끝에서 다음 행으로 자동 이동하지 않습니다.

방향step이동
right(w, 0)오른쪽으로 너비만큼
left(−w, 0)왼쪽으로 너비만큼
down(0, h)아래로 높이만큼
up(0, −h)위로 높이만큼

네 방향은 현재의 잠정 권장안입니다. 참조하는 추출 사각형이 이미지 밖으로 나가면 오류이고, 등록만 한 미사용 이미지는 열 필요가 없습니다. 글리프마다 크기·위치가 다른 불규칙 패킹은 미결 사항입니다.

03

가져오기와 배치

원문 §3 ↗

at은 글리프의 인덱스를 고르고, offset은 그 글리프의 픽셀을 옮깁니다.

B에 8 × 8 글리프 6개, A에 10 × 8 글리프 10개가 있다고 합시다. 아래는 A의 임포트 한 개입니다.

A.imports의 한 항목
{
  "group": "B",
  "offset": [1, 0],
  "at": [
    {"from": [0, 3], "to": 5}
  ]
}
가져올 부품배치할 대상
B[0]→A[5]
B[1]→A[6]
B[2]→A[7]

각 부품을 대상의 로컬 좌표 (1, 0)에 놓습니다.

끝은 포함하지 않습니다.

from: [0, 3]은 0·1·2번입니다. 일반적으로 0 ≤ j < b − a일 때, source[a + j]를 target[t + j]로 가져옵니다.

imports와 그 안의 at은 순서가 있는 목록입니다. 같은 B를 다른 오프셋으로 다시 가져와도 됩니다. 여러 규칙이 같은 대상 인덱스에 도착하면 이전 결과를 덮어쓰지 않고, 그 위에 별도 레이어로 놓입니다.

04

중첩 반복

원문 §3 · §7 ↗

같은 배치를 여러 번 펼칩니다. 반복 축을 겹치면 여러 인덱스 차원의 곱을 표현할 수 있습니다.

repeat는 축의 목록입니다. 첫 축이 바깥쪽, 마지막 축이 안쪽 반복입니다. 각 축의 count는 양의 정수이며, from_stride의 기본값은 0, to_stride의 기본값은 가져오는 구간 길이 b − a입니다. 생략하면 []과 같고, 축 하나도 목록으로 씁니다.

가져올 인덱스a + j + Σ(kₘ × from_strideₘ)
배치할 인덱스t + j + Σ(kₘ × to_strideₘ)

0 ≤ j < b − a · 각 축에서 0 ≤ kₘ < countₘ

3개씩, 두 축으로 반복하기

원문 Grid 예제의 at 규칙입니다. 소스 B는 6개, 대상 Grid는 12개 글리프를 가집니다.

Grid의 at 규칙
{
  "from": [0, 3],
  "to": 0,
  "repeat": [
    {"count": 2, "from_stride": 3, "to_stride": 6},
    {"count": 2, "from_stride": 0, "to_stride": 3}
  ]
}
반복을 펼친 순서k₀ → k₁ → j
  1. 01k₀=0, k₁=0B[0..2]→Grid[0..2]
  2. 02k₀=0, k₁=1B[0..2]→Grid[3..5]
  3. 03k₀=1, k₁=0B[3..5]→Grid[6..8]
  4. 04k₀=1, k₁=1B[3..5]→Grid[9..11]
선택한 배치의 인덱스B[0] → Grid[0] · B[1] → Grid[1] · B[2] → Grid[2]

안쪽 축은 같은 부품을 다른 대상에 반복합니다. 바깥쪽 축은 다음 부품 묶음으로 넘어갑니다. 펼친 뒤의 소스·대상 인덱스는 모두 각 그룹의 범위 안이어야 합니다. 음수 stride도 가능하지만 범위를 벗어나서는 안 됩니다.

05

레이어와 클리핑

원문 §3 · §5 ↗

자기 텍스처가 첫 레이어입니다. 가져온 레이어는 선언 순서대로 그 뒤에 놓입니다.

  1. 1
    자기 텍스처

    있다면 먼저 놓습니다.

  2. 2
    첫 번째 import

    at 규칙과 반복 인덱스 순서를 따릅니다.

  3. 3
    다음 import

    같은 대상을 참조해도 독립된 레이어입니다.

01소스 경계로 자르기[0, wₛ) × [0, hₛ)
↓
02오프셋 적용하기(dx, dy)
↓
03대상 경계로 자르기[0, wₜ) × [0, hₜ)
중간 경계도 남아 있습니다.

C → B → A라면 C·B·A의 경계를 각각 적용합니다. B에서 잘린 픽셀은 A의 오프셋이 되돌아오더라도 복구되지 않습니다. 최종 오프셋만 더해 평탄화하면 이 의미를 잃을 수 있습니다.

여기까지가 명세가 정하는 구조입니다. 겹친 픽셀을 알파 합성할지, 마스크로 결합할지, 색·샘플링을 어떻게 처리할지는 렌더러가 문서화할 정책입니다. 서로 다른 렌더러의 최종 픽셀이 반드시 같아야 하는 것은 아닙니다.

06

유니코드 매핑

원문 §4 ↗

글리프를 구성하는 일과, 그 글리프에 문자를 연결하는 일은 별개입니다.

그룹의 unicode 필드
[
  {"from": [0, 3], "to": "U+AC00"}
]
G[0]→U+AC00가
G[1]→U+AC01각
G[2]→U+AC02갂
  • 매핑은 선택 사항입니다. 매핑이 없는 그룹도 다른 그룹의 부품으로 쓸 수 있습니다. 매핑한 글리프만 내보내기 후보가 됩니다.
  • 임포트가 문자 매핑을 물려받지는 않습니다. 가져온 부품이 어떤 문자에 연결되어 있어도, 대상 그룹의 매핑은 따로 선언합니다.
  • 다른 글리프가 같은 코드 포인트를 차지하면 오류입니다. 반대로 같은 그룹의 같은 글리프를 여러 코드 포인트에 연결하는 별칭은 허용됩니다.
  • 유니코드 스칼라 값만 허용합니다. U+0000부터 U+10FFFF까지 중 서로게이트 구간 U+D800–U+DFFF는 제외합니다. 범위 전체가 이 조건을 만족해야 합니다.

오른쪽 표는 인덱스와 코드 포인트의 연결을 보여 줍니다. 매핑 자체가 가·각·갂의 모양을 만들어 주지는 않습니다. 보이는 이미지가 없는 공백 글리프도 유효합니다.

07

한글 조합 예제

원문 §7.1 ↗

8 × 4 × 4벌은 글자의 개수가 아니라, 문맥에 따라 고르는 자모 모양의 벌 수입니다.

hangul.png ↗432 × 256 px
초성
8 × 19152개
중성
4 × 2184개
종성
4 × 27108개
전체 부품
344개

셀 하나는 16 × 16 픽셀이고, 27열 × 16행으로 놓여 있습니다. 각 벌의 예약된 첫 빈 셀은 제외되어 있으며, 오른쪽의 남는 셀은 참조하지 않습니다. 받침이 없는 경우에는 종성 부품을 가져오지 않습니다.

문자 순서를 인덱스 식으로 표현하기

i = 588L + 28V + T코드 포인트 = U+AC00 + i
인덱스범위뜻to_stride
L[0, 19)유니코드 초성 순서588
V[0, 21)유니코드 중성 순서28
T[0, 28)종성 순서. 0은 받침 없음1

예를 들어 가는 (L,V,T) = (0,0,0), 인덱스 0입니다. 각은 (0,0,1), 인덱스 1입니다. 19 × 21 × 28 = 11,172자를 U+AC00–U+D7A3에 연결합니다.

초성은 중성 모양과 받침 유무에 따라 무받침 5벌·유받침 3벌 중 하나를 고릅니다. 중성 4벌은 초성이 ㄱ·ㅋ인지, 받침이 있는지에 따라 고릅니다. 종성 4벌은 중성에 따라 고릅니다. 이 선택은 imports와 중첩 repeat로 표현되어 있으며, 렌더러에 한글 조합을 하드코딩하지 않습니다.

hangul.json은 한글에 ASCII 95자를 더해 11,267자를 매핑합니다. ascii.json은 ASCII만 있는 별도 예제입니다. ASCII는 8 × 16 셀의 텍스처를 행별로 나눕니다. 추출 방향이 다음 행으로 자동 줄바꿈하지 않기 때문입니다.

이 예제는 8×4×4벌 참고 문서의 모양 구분을 유니코드 순서에 맞춘 것입니다. 옛 조합형 코드의 인코딩·예약 셀·C 배열 오프셋을 그대로 재현한 것은 아닙니다.

예시 텍스처 글꼴 출처: IT문화원 글꼴 자료.

08

유효성 검사

원문 §6 ↗

선언만으로 알 수 있는 오류와, 이미지 크기를 알아야 검사할 수 있는 오류를 구분합니다.

검사 대상유효한 조건오류의 예
설명 필드metadata는 매핑, 이름·버전·저자는 문자열. 그룹 설명도 문자열"version": 3
이름과 경로그룹 이름은 고유. 셋 이름과 셋 내부 소스 이름은 비어 있지 않고 고유. 경로는 비어 있지 않은 문자열같은 셋에 동일한 소스 이름 두 번 등록
참조모든 그룹·셋·소스가 존재하고 그룹 참조에 순환이 없음A → B → A
크기와 개수size의 두 값과 그룹 count가 양의 정수"size": [0, 16]
배치와 반복0 ≤ a < b, 축의 count는 양의 정수. 펼친 모든 인덱스가 범위 안count가 6인 소스에서 6번 가져오기
텍스처 추출이미지 크기를 알면 참조하는 추출 사각형이 이미지 안에 있어야 함너비 32인 이미지에서 x=32부터 8픽셀 추출
문자 매핑그룹 인덱스·스칼라 값 범위 안. 다른 글리프 간 코드 포인트 충돌 없음서로 다른 글리프에 U+AC00 중복 배정

빈 이미지나 유니코드 매핑이 없는 그룹은 오류가 아닙니다. 이미지가 아직 로드되지 않았더라도 선언된 셋·소스 이름의 참조는 유효해야 합니다. 경로는 이미지 자원을 가리키는 값이지 참조 이름이 아닙니다.

09

명세의 경계

원문 §5 · §8 ↗

공통으로 정하는 것은 레이어 구조입니다. 픽셀을 그리는 정책과 폰트 출력 설정은 그 다음 단계입니다.

명세가 정합니다

  • 어떤 그룹의 어떤 인덱스를 참조하는가
  • 어느 좌표에 어떤 순서로 놓는가
  • 각 그룹 경계에서 어디를 자르는가
  • 어느 코드 포인트에 연결하는가

렌더러·출력 설정이 정합니다

  • 알파 합성 또는 마스크 결합
  • 색·투명도·샘플링 처리
  • TTF 윤곽선 변환
  • 기준선·글리프 전진 폭·폰트 단위 변환

렌더러 정책이라고 해서 참조·배치·순서·클리핑을 임의로 바꿀 수는 없습니다. 필요한 이미지 형식이나 연산을 지원하지 못하면 명시적으로 알려야 합니다. 현재 저장소에는 TTF 생성기가 없습니다.

아직 정하지 않은 사항

  1. 추출 방식

    방향을 네 가지로 제한할지, 줄바꿈·간격·글리프별 사각형을 추가할지.

  2. 저장 형식과 경로

    구체적인 직렬화 형식·스키마와 이미지 경로 해석 규칙. 현재 검사기는 선언 파일의 디렉터리를 기준으로 상대 경로를 해석합니다.

  3. 출력 설정

    렌더링 및 글리프 메트릭 설정의 구체적인 스키마.

검사기에서 바로 확인하기

Python 3.11 이상과 uv가 필요합니다. 저장소 루트에서 시작합니다.

터미널 · 저장소 루트에서
cd tools/inspector
uv sync

# 텍스처 없이 선언과 그룹 관계 조회
uv run glyph-inspect groups ../../examples/hangul.json

# 실제 PNG를 조합해 한글 문자 미리보기
uv run glyph-inspect text ../../examples/hangul.json \
  --text '짜임 가각나' --output text.png

두 브라우저 편집기는 GitHub Pages에서 설치 없이 이용할 수 있는 별도 프로그램입니다. 로컬 파일로 실행하려면 저장소 루트에서 python3 -m http.server 8000으로 파일 서버를 열면 됩니다. 빌드·CDN·애플리케이션 백엔드는 필요하지 않습니다.
